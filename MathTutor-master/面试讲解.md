## 一、一句话定位

> 一个把 LLM 从"单次问答"升级为"**可纠错、可记忆、可检索、可调工具**"的垂直领域多智能体系统——用系统工程的手段补上单次 LLM 调用的四大缺陷：**会算错、会瞎编、不记人、不会用工具**。

---

## 二、项目背景：要解决什么问题

**直觉方案**：`用户输入 → 问一次 LLM → 返回答案`。

**为什么不够**（这是整个项目存在的原因）：

| 缺陷 | 具体表现 | 我的解法 |
|---|---|---|
| ① 会算错 | LLM 解方程第 3 步符号就错了，还自我感觉良好 | **独立 Verifier 校验 + 最多 3 轮自纠错** |
| ② 会瞎编 | 忘了公式就编一个，学生被误导 | **Hybrid CRAG：检索资料再回答，检索不到就明说** |
| ③ 不记得学生 | 昨天说"我不会二次函数"，今天全忘 | **三层长期记忆 + 向量召回 + 记忆衰减** |
| ④ 不会用工具 | 算大数硬算、要查资料时凭空发挥 | **ReAct 循环 + Tool Calling + MCP** |

## 四、核心设计决策（每个都是面试考点）

### 决策 1：为什么用 LangGraph 图编排，而不是 LangChain Chain？

- **Chain 是线性管道**（A→B→C 写死），表达不了循环、回跳、分支
- Agent 流程是**运行时动态决定**的：要不要重试？要不要调工具？要不要问人？
- LangGraph 的 `StateGraph` + `Conditional Edge` 天然表达这些

**关键代码**（自纠错循环的条件边）：

```python
graph.add_conditional_edges(
    "verifier_agent",
    _route_after_verifier,          # 读 state 决定去向
    {"safety_agent": "safety_agent",   # 正确 → 放行
     "solver_agent": "solver_agent",   # 错误且<3次 → 打回重做
     "hitl_node":    "hitl_node"},     # 无法判定/超3次 → 人工
)
```

**追问**：`AgentState` 是共享可变对象，会不会数据污染？
**答**：LangGraph 的状态更新按 key 合并（reducer），节点只返回自己负责的字段增量，不覆盖他人——框架层保证，无需自己加锁。

### 决策 2：为什么把"解题"和"验证"拆成两个节点？

- **自己检查自己永远不靠谱**——必须独立裁判
- solver 负责生成，verifier 按三标准校验：① 步骤正确性 ② 单位/定义域 ③ 边界情况
- verifier 输出 `suggested_fix`（具体错在哪一步、该怎么改），**作为反馈注入 solver 下一次的提示词**

```python
# solver 重试时注入校验反馈
feedback_block = f"\n\n上一次尝试不正确。\n校验反馈：{feedback}"
```

**追问**：3 轮还错怎么办？
**答**：转 HITL 人工介入；人工判定后还可以把结果**送回 solver 继续**（`_route_after_hitl` 里的 verification 分支），形成"人机协同"。

### 决策 3：为什么做 6 类意图路由？

- **不同意图的成本和严谨度要求完全不同**：解题必须验证（贵但严谨），讲解直接回答即可（快）
- 路由 = **把最贵的资源只花在最需要的地方**

```
"帮我解 x²-5x+6=0"   → solve      → 完整解题管线（验证+重试）
"什么是贝叶斯定理"     → explain    → 直接回答（不验证）
"给我出 5 道概率题"   → generate   → 直接回答 + 联网搜索
```

### 决策 4：为什么 Hybrid CRAG（双路检索 + 融合 + 纠错）？

**单路检索的盲区**：
- 纯向量（FAISS）：语义强，但"公式符号"这种字面匹配会漏
- 纯词法（BM25）：字面强，但"抛物线的对称轴"匹配不到"二次函数顶点公式"

**三步流水线**：

```
查询 → FAISS 稠密 Top-10 ──┐
                         ├→ RRF 融合(按排名加权) → Top-5 → 余弦相似度过滤(≥0.30)
查询 → BM25 稀疏 Top-10 ──┘                                              │
                                                                         ▼
                                                        过滤后为空 → 明确告知"没找到"
                                                                   → 引导换 web_search
```

**为什么最后要余弦过滤**：RRF 只保证"两条路线都认可"，但 BM25 可能因词频把不相关段落排高——余弦相似度是**语义层面的最终确认**，宁可漏检（触发兜底）也不给 LLM 喂噪声。

**追问**：RRF 为什么按排名不按分数？
**答**：两条路线的原始分数量纲不同（余弦 vs BM25 分数），直接加会失衡；按排名算 `1/(K+rank)` 天然免疫分数尺度差异。

### 决策 5：为什么三层记忆？（Episodic / Semantic / Procedural）

**三类信息生命周期和用途完全不同，必须分开存**：

| 层 | 存什么 | 生命周期 | 为什么单独一层 |
|---|---|---|---|
| Episodic 情景 | 每道做过的题（题目/答案/对错） | 90 天 TTL + 遗忘衰减 | 会过期，**可清理** |
| Semantic 语义 | 弱项统计（`algebra: 3 次`） | 永久 | 学生画像，**不能丢** |
| Procedural 程序 | 哪个方法对这个学生有效 | 永久 | 教学策略 |

**为什么记忆要向量化**：跨会话召回——新会话问"求抛物线的对称轴"，要找到昨天那条"我不会顶点公式"。关键词找不到（表述完全不同），**BGE 向量 + RedisVL HNSW 语义检索**才能找到。

**为什么检索带副作用**：每次召回 `access_count+1` 并刷新 `decay_score = e^(-days/30) × log(1+count)`——**越常被回忆的记忆越牢固**（模拟艾宾浩斯遗忘曲线），记忆是活系统，不只是存储。

**为什么用 RedisVL 不用 FAISS 存 LTM**：FAISS 是进程内存索引（会话结束即消失）；LTM 检索必须①按 `@student_id` 过滤②检索后更新计数/衰减③返回完整 JSON 记录——**RedisJSON + RedisVL 存查一体**，无需维护两套系统一致性。

### 决策 6：为什么接入 MCP？

- MCP 是行业标准协议，**"一次接入，处处可用"**
- Tavily 提供远程 MCP 服务器，`fastmcp` 客户端一行 `call_tool` 调用，无需自己对接搜索 API

```python
async with FastMCPClient(server_url) as client:
    result = await client.call_tool("tavily_search", {"query": query, ...})
```

## 五、难点攻坚（面试最值钱的部分，全是真实踩坑）

### 难点 1：元认知查询失效——"我有哪些知识点不会"答不上来

**现象**：学生新会话问"我有哪些知识点不会"，Agent 答不上来，长期记忆像没生效。

**排查过程**（查数据 → 读代码 → 定位根因）：
1. 查 Redis：`semantic` 记录数 = **0**（弱项档案是空的），episodic 却有 5 条
2. 读代码发现 **flow gate**：semantic/procedural **只在 solve 流程写入**
3. 根因：学生说"我不会二次函数"被路由为 `explain`（非 solve）→ **用户亲口暴露的弱项信号被设计逻辑丢弃了**，只留在了 episodic 文本里

**修复方案**（三处改动 + 数据迁移）：
1. **存储侧**：非 solver 流程检测弱项信号词（"不会/不懂/没掌握/薄弱"等）→ 也写入 semantic
2. **读取侧**：新增 `build_student_profile()` 读完整档案（全量弱项/强项/历史聚合），替代只针对当前 topic 的旧接口
3. **回答侧**：检测元认知查询（"哪些知识点不会/弱项/学习情况"）→ 走专门档案 prompt，**如实回答，档案为空就明说**
4. 一次性脚本迁移已有 5 条 episodic 里的弱项信号进 semantic

**追问**：为什么向量检索再强也救不了这个 bug？
**答**：**检索只能召回已存在的数据**——弱项信号没进 semantic 层，HNSW 再准也召不回不存在的东西。这暴露的是**写入侧的数据链路缺失**，不是检索质量问题。

### 难点 2：DeepSeek 结构化输出兼容

**现象**：`with_structured_output()` 默认的 `json_schema` 方式在 DeepSeek 上报 400（`This response_format type is unavailable now`）。

**排查**：DeepSeek 不支持 OpenAI 风格的 json_schema response_format；json_mode 又要求提示词含"json"字样。

**解决**：6 个节点统一改为 `method="function_calling"` 走函数调用协议实现结构化输出。

### 难点 3：RedisVL 向量检索"静默失效"

**现象**：LTM 检索永远返回 0 条，但代码不报错。

**排查发现三个坑**：
1. **filter 语法**：多条件必须加括号 `(@a:{x} @b:{y})`，否则 Redis 报 Syntax error——**且异常被 try/except 吞掉**，导致静默失败
2. **索引字段限制**：RedisVL 只返回 schema 声明的字段，`problem_summary` 等没声明的拿到 None，需用 id 从 RedisJSON 补全
3. **topic 精确匹配陷阱**：`@topic:{topic}` 会让跨主题相似题永远检索不到，改为只按 `@student_id` 过滤，靠向量相似度排序

**教训**：**被 try/except 吞掉的异常是最危险的 bug**——系统不报错，但功能静默失效。排查时先怀疑"吞异常"。

### 难点 4：BGE 模型加载联网超时

**现象**：启动报 `WinError 10060`，程序尝试从 huggingface.co 下载模型失败（网络不通）。

**解决**：模型已本地缓存，设置 `HF_HUB_OFFLINE=1` + `TRANSFORMERS_OFFLINE=1` 走离线加载，写入启动脚本固化。

## 六、工程化实践

### 78 个自动化测试怎么组织的

**核心思想**：把"确定性业务规则"从"不可控 LLM 行为"中剥出来——**LLM 输出不可控不测（人工评测），业务规则必须测（自动化）**。

**三层策略**：
1. **环境隔离**（conftest.py）：`sys.modules` 注入假模块（假 Redis/假 RedisVL/假 Groq），`ChatGroq.invoke` 故意 raise——**测试忘了 mock 会立刻报错**
2. **单元测试**：`VerifierAgent.__new__` 跳过 `__init__` + 假 LLM 返回固定结果，直测真实方法逻辑；**计数 spy**（lambda 替换存储函数）验证"什么流程触发什么写入"
3. **集成测试**：monkeypatch 所有节点 LLM，跑完整 graph 链路验证路由契约

**CI**：GitHub Actions 每次 push/PR 自动跑全量测试 → **规则被破坏立刻红灯，不等用户踩雷**。

**追问**：78 个测试覆盖了什么？漏了什么？
**答**（诚实）：覆盖的是纯逻辑层（路由/门控/重试上限/解析），**没有覆盖**真实 LLM 输出质量、向量检索效果——那是评测集（eval set）的范畴。测试保证"系统不崩、规则不坏"，不保证"回答质量高"。

## 七、面试官高频追问速查

| 追问 | 一句话回答 |
|---|---|
| 为什么用 LangGraph？ | Chain 是线性管道，表达不了循环/回跳/分支；Agent 流程运行时才决定走向 |
| 为什么 15 个节点？ | 职责单一才能独立测试、独立替换；verifier 必须独立于 solver |
| 为什么双路检索？ | 语义+字面互补，单路都有盲区 |
| 为什么最后要余弦过滤？ | RRF 保证"两条路线都认可"，余弦过滤是语义层面最终把关 |
| 为什么三层记忆？ | 生命周期不同：episodic 可清理，semantic/procedural 永久 |
| 检索为什么带副作用？ | 模拟遗忘曲线，越常被召回的记忆越牢固 |
| RedisVL vs FAISS？ | 前者服务端持久化+结构化过滤+JSON 一体；后者进程内存，服务会话内 RAG |
| 78 个测试能防住什么？ | 钉死业务规则：门控、重试上限、路由契约；不测 LLM 输出质量 |
| 最大的坑是什么？ | 元认知查询失效——暴露"写入侧数据链路缺失"比"检索不准"更隐蔽 |

## 八、项目亮点总结（3 句话讲完）

1. **工程化补 LLM 短板**：verifier 自纠错闭环 + Hybrid CRAG + 三层记忆 + MCP 工具，把"不可控的单次调用"变成"可控的系统工程"
